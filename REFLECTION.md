
# Project #1: Applicant Tracking System

## Question 1 — Trace Your Django Forms

In my Applicant Tracking System, I examined two different Django forms: ApplicationForm, which inherits from forms.Form, and CandidateForm, which inherits from forms.ModelForm.

ApplicationForm is used when an employee creates an application connecting a candidate to a job opening. The employee begins from a candidate or opening page, and the form provides eligible choices for the other side of the application. It checks that the candidate is not archived, the opening is not closed, and the same candidate has not already applied to that opening. After validation, its save method creates the application and records the employee and initial hiring-stage information.

CandidateForm is used to create and update candidate records. The candidate creation and update views use this form to collect information associated with the Candidate model and save the record.

The important difference is that forms.Form requires the developer to define the fields and saving behavior manually, while forms.ModelForm is connected to a model and provides built-in functionality for creating or updating its records. The application form needs additional custom logic because it connects two existing records and must enforce specific hiring rules.

## Question 2 — Trace a Many-to-Many Relationship

One many-to-many relationship in my ATS connects candidates and job openings. A candidate can apply to multiple openings, and each opening can have multiple candidates.

A single foreign key would not correctly represent both sides of this relationship. My project therefore uses an explicit association model called Application, which connects Candidate and JobOpening using two foreign keys.

The Application model also stores information belonging to that specific application, including its current hiring stage, previous stage, the employee who last changed the stage, and timestamps.

This association model is defined explicitly in the project rather than being automatically generated by Django. It also has a uniqueness constraint preventing duplicate applications for the same candidate and opening.

This design is useful because an application represents more than just a connection between two records. Each application has its own hiring progress and rules.

## Question 3 — Explain One Prototype Decision

For my UI prototype, I compared three hiring-dashboard designs: a Kanban board, a table view, and an openings-first workspace.

The Kanban board organized applicants into columns for each hiring stage. The table emphasized searching, sorting, and filtering. The openings-first workspace organized navigation around job openings, with a sidebar, stage summary, applicant list, and detail panel.

I approved the openings-first workspace because I wanted employees to navigate applicants by job opening without dealing with eight separate Kanban columns. I felt that a Kanban layout could become difficult to use with many applicants because of the horizontal space it required.

However, I liked the table prototype's search, sorting, and filtering features. I decided to combine those features with the openings-first design rather than choosing the entire table layout.

The final ATS follows that decision. Its hiring workspace uses the openings sidebar and applicant detail panel, while Phase 10 adds search, stage filtering, and sorting.

This prototype helped me see how comparing alternatives before coding can lead to a better design.

## Question 4 — Defend One Code-Design Decision

One architecture decision I approved was keeping the hiring-stage transition rules in a separate Python module instead of putting all the rules directly in views or repeating them in different parts of the application.

The alternative was to handle transition restrictions wherever employees performed stage-change actions. However, repeating the rules could make them harder to maintain and could result in inconsistent behavior.

I approved a separate rules module because the ATS has several important restrictions. Employees can move applicants forward, skip ahead, or move an active application to Rejected or Withdrawn. Normal backward movement is prohibited, and Hired is permanent.

I also approved an Undo feature that restores an eligible application's actual previous stage. To prevent an outdated confirmation from overwriting a newer change, the implementation validates both the expected stage and the stage-change timestamp.

The separate rules module is used by the application's move and Undo methods and by the hiring workspace when deciding which actions to display.

I learned that separating business rules from the interface makes code easier to test, reuse, and maintain.
